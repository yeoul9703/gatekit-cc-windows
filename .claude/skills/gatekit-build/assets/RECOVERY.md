# {{project_name}} — 복구 절차

빌드가 실패했을 때 무엇을 하는지 정한다. 즉흥적으로 고치지 않기 위한 문서다.

## 진단 루프

한 번에 하나씩, 순서대로 한다. 단계를 건너뛰지 않는다.

1. **증상을 그대로 적는다.** 실패한 기준 id, 종료 코드, stderr 꼬리 5줄.
   해석하지 말고 관측값만 적는다.
2. **가설을 하나 세운다.** "무엇이 잘못됐을 것이다"를 한 문장으로.
3. **가설을 반증할 수 있는 관찰을 정한다.** 가설이 틀렸다면 무엇이 보일 것인가.
4. **관찰한다.** 로그·테스트·최소 재현. 가설이 살아남지 못하면 2로 돌아간다.
5. **최소 수정을 한다.** 원인 한 곳만 고친다. 여러 곳을 동시에 고치면
   무엇이 효과가 있었는지 알 수 없게 된다.
6. **같은 기준을 다시 실행한다.** `uv run --project .claude/gatekit --frozen python .claude/gatekit/bin/gatekit.py contract run`.

## 재시도 한도

| 대상 | 한도 | 넘었을 때 |
|---|---|---|
| 작업 하나의 재시도 | 3회 | 중단하고 사람에게 보고한다. 4회째를 시도하지 않는다. |
| Stop 훅의 차단 | 3회 | 차단을 풀고 `final_verdict`를 기록한다. 무한 루프를 만들지 않는다. |
| 같은 가설의 재검증 | 1회 | 두 번째로 같은 가설이 틀리면 가설을 바꾼다. |

한도를 넘었다는 것은 진단이 틀렸다는 신호다. 더 세게 시도하는 것이 아니라
문제를 다시 정의한다. 보고에는 시도한 것과 각각이 왜 실패했는지를 남긴다.

## 범위 잠금

- 실패를 고치는 동안 `write_scope`를 넓히지 않는다. 범위 밖 파일이 원인이면
  범위를 늘리는 대신 그 사실을 보고하고 작업을 다시 나눈다.
- 실패한 테스트를 지우거나 `skip` 처리하지 않는다.
- `spec/05-gate.md`의 기준을 완화하지 않는다. 기준이 틀렸다면 사람이 다시
  승인해야 한다.
- 관계없는 리팩터링을 끼워 넣지 않는다.

## 롤백 절차

1. 현재 시도의 산출물을 `.gatekit/jobs/<job_id>/tasks/<id>/attempt-N/`로 보존한다.
2. 작업 범위의 파일을 마지막으로 게이트를 통과한 상태로 되돌린다.
   `git restore -- <write_scope 경로>` 또는 `git checkout <sha> -- <경로>`.
3. `PROGRESS.md`의 "실패한 시도" 표에 한 줄 추가한다.
4. 게이트를 다시 실행해 되돌린 상태가 실제로 통과하는지 확인한다.
   확인 없이 다음 작업으로 넘어가지 않는다.

되돌릴 지점이 없다면(커밋이 없다면) 롤백 대신 중단하고 사람에게 보고한다.
