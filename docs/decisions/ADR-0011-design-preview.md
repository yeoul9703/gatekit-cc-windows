# ADR-0011: Show the screens before the build, and send what the owner fixed to the workers

Status: proposed 2026-09-17.

Origin: the Tetris trial. `spec/01-prd.md` assumption 17 and the hand-made
`spec/design/preview-tetris.html`; the owner's report of what hurts most in
vibe coding: *"설계문서 다 뽑고 다 완성된 뒤에 디자인을 볼 수 있었던 점이야,
코딩 구현 전에 정지된 화면이라도 상관 없으니 미리보기가 가능할까?"* — and,
on reading the first draft of this ADR: *"미리보기 한 디자인이 출력결과에
반영이 안되면 의미가 없는 거잖아."*

## Context

`/gatekit:mockup` writes `spec/02-screens.md`. With no design source to read,
the screens are designed from the PRD rather than observed. The Tetris trial
ran that way: four screens, nine transitions, sixteen states, all prose. The
owner could read that the pause overlay is `color.canvas-parchment` at 80%
with `effect.frosted`, but could not see it until six workers had run.

Mid-trial a preview was written by hand to `spec/design/preview-tetris.html` —
drawn only from `02-screens.md` and `tokens.json`, before any game code
existed — and it worked. It was simply outside the pipeline.

### The part the first draft got wrong

A preview is worth nothing if what the owner fixes does not reach the build.
Today it partly does not.

`jobs.build_prompt` already injects a `## Design` section into every worker
brief, generated by code from `tokens.json` (ADR-0008): the matching `P<n>`
pattern rows and every token as `group.name: value`. That is why the trial's
colours and spacing matched the preview.

But the screen layout is not injected. The section ends with a pointer:

```
Read spec/02-design.md and spec/02-screens.md for anything not listed here.
```

So "hold box on the left, next three on the right" reaches the worker only if
it chooses to open the file. Tokens are pushed; layout is hoped for. A preview
whose corrections land in `02-screens.md` would inherit exactly that weakness.

The standing constraints apply: standard library only; hooks and code are the
enforcement, not prose; `unverified` never rounds; tests first.

## Decision

Three changes. No new pipeline stage, no new gate, no approval record.

### 1. `/gatekit:mockup` offers a preview when it had no design source to read

After `spec/02-screens.md` validates, one `AskUserQuestion` in `output_lang`:
see the preview, or go straight on. This reuses the command's existing
question budget (`mockup.md` step 7 already spends at most one), so nobody is
asked twice, and a stop signal ("알아서 해줘") suppresses it as it suppresses
the current question.

An input-driven run (`/gatekit:mockup <figma-url>`) does not offer it. There
the screens were observed, and drawing them adds nothing.

### 2. The preview is drawn from the spec, shown, and corrected in place

`spec/design/preview-<project>.html`, one section per `S<n>`, built from
`spec/02-screens.md` (layout, components, the four states) and
`spec/tokens.json` (every value). `spec/**` is already in the write gate's
allowlist, so it writes before `05-gate.md` approval with no gate change.

Its first visible element is a banner, in `output_lang`, with this meaning
fixed:

> 이 미리보기는 대략적인 디자인 패턴일 뿐, 실제 구현 결과는 다를 수 있습니다.
> 여기 보이는 화면은 관찰된 것이 아니라 명세에서 그린 것입니다.

The banner is the responsibility boundary: what the owner is looking at is the
*screen spec*, not the product.

Then the loop, which is the whole review mechanism:

1. Show the preview.
2. The owner says what to change, in their own words.
3. Edit `spec/02-screens.md` — the spec is what changes, never only the HTML.
4. Redraw from the edited spec and show it again.
5. Repeat until the owner is done.

**Nothing is recorded as approved.** The screens stay assumptions in the
ledger exactly as they are today, and assumption 17 stays open. The owner's
corrections are carried by `02-screens.md` itself, which is where the build
reads from. An approval record was in the first draft of this ADR and is
dropped: it added a step and a validation rule to produce a line of provenance
nobody had asked for.

Limits that keep the drawing cheap:

- **Static.** No interactivity. The four states of a screen are drawn as four
  panels, not something to click. It answers "what does it look like", never
  "how does it behave".
- **Tokens only.** Every value comes from `tokens.json` by name. A value the
  tokens do not carry is not invented for the drawing; the region is drawn as
  a labelled placeholder naming what is missing, so the preview cannot quietly
  become a second, unversioned design source.
- **One file**, under the repo's 1 MB limit, no external requests, no build
  step.

### 3. The screen spec is injected into the worker brief, like tokens already are

`jobs._design_lines` gains a `## Screens` block: for each `S<n>` the task's
title or instruction mentions, the screen's layout line and its four state
rows, copied from `spec/02-screens.md`. Same mechanism as the `P<n>` pattern
rows — matched by the same `S<n>` scan that `_pattern_applies` already does,
generated by code, so nothing depends on a task author having written "read
the screen spec" or on a worker choosing to open the file.

This is what makes decision 2 worth doing: a correction the owner makes at
preview time lands in `02-screens.md`, and `02-screens.md` now reaches the
worker as text in its brief rather than as a pointer.

The block is **bounded twice**, unlike the token lines beside it: each copied
paragraph or state row is clipped at `SCREEN_TEXT_MAX_CHARS` (1200) and the
whole block at `SCREENS_BLOCK_MAX_CHARS` (8000), with the cut made visible and
any dropped screens named. Token lines are `name: value` scalars and cannot
individually grow; spec prose has no natural limit, and an unbounded paragraph
would become an unusable worker stdin rather than a better brief.

`parse_screens` is **fence-aware**: inside a ``` or `~~~` block every line is a
picture of markdown, so a `### S9` drawn in a flow diagram names no screen and
a `|` line is not a state row. It also honours `\|` as a literal pipe inside a
cell. Both were real defects found in review — without them a fenced diagram
silently deleted the following screen's state rows and invented a phantom
screen, which is the exact failure this ADR exists to prevent, arriving as a
brief that looks complete.

*Revised at review (2026-09-17): the block also emits when `tokens.json` is
absent, so a project with screens but no design tokens still gets its layout.
The first draft said `_design_lines` "gains" the block, which would have tied
it to `has_design`; the looser placement is deliberate and recorded here
rather than left as an undocumented divergence.*

Two properties this inherits for free, both already true:

- `spec/02-screens.md` is in `contract.INPUT_FILES` (ADR-0008), so editing it
  after the gate is approved makes the contract `contract_stale` and the build
  stops rather than proceeding on the old basis.
- A task that names no `S<n>` gets no `## Screens` block, exactly as a task
  that matches no pattern gets no pattern rows.

The block is bounded: layout line plus four state rows per screen, and only
for screens the task names. A task naming every screen carries every screen,
which is correct — that is what it was asked to build.

### 4. The preview file is never cited as evidence

`spec validate` fails when an evidence cell in `02-screens.md` or
`02-design.md` cites a `spec/design/preview-*.html` path. The preview is
drawn *from* the spec; citing it back would let the spec corroborate itself.
`/gatekit:design` refuses a preview file passed as its input for the same
reason.

Two carve-outs, both found in review. A **remote URL is spared** whatever it
is named: fetching a live page is observation, and `/gatekit:design` now tells
users to supply exactly such a source, so failing a row citing a vendor's own
`preview-widget.html` would reject the evidence this rule exists to protect.
A **row inside a fenced block is spared** too — a fenced example of a bad row
is documentation of the rule, not an instance of it.

The check is deliberately narrow and easy to evade (`preview-demo.htm`,
`preview_demo.html` all pass). It stops the accident — a preview cited because
it was the last file drawn — not a determined author. It exists because
decisions 1–3 are prose in a command file, and prose is never an enforcement
mechanism in this repo.

### 5. Command text

`mockup.md` gains the offer, the draw-show-correct loop and the banner
requirement. `design.md` gains one sentence refusing a preview as input.

## Consequences

**What the owner gets.** A picture before the build, at the point where
changing a screen costs one line of Markdown instead of a redelegated task —
and a correction that actually reaches the workers, because the screen spec is
now pushed into the brief rather than pointed at.

**What it does not give.** Nothing about behaviour. The trial's own record
makes this concrete: the swipe binding (F4) was missing because `main.js`
never imported `bindTouch`, and no static drawing of S2 would have shown it.
Feel, drop speed and timing likewise. The preview closes "I couldn't see it"
and leaves "I couldn't try it" open.

**Honest limit.** The drawing is produced by a model, so nothing guarantees it
faithfully represents the spec, and injecting the screen text does not
guarantee a worker follows it — the trial showed a worker writing colours that
were in the brief's token list and still wrong, caught by the tokens gate
rather than by the prompt. Decision 3 raises the odds; it does not enforce.
Enforcing screen fidelity mechanically is left out of scope on purpose.

**Costs.** `/gatekit:mockup` grows a branch and a redraw loop. Worker prompts
grow by roughly fifteen lines per screen a task names. `spec validate` grows
one check.

**Contract changes** (`docs/ARCHITECTURE.md`): §2 lists
`spec/design/preview-<project>.html`; §10 notes that `## Design` now carries a
`## Screens` block built from `02-screens.md` for the `S<n>` a task names;
the mockup pipeline section states the offer, the static and tokens-only
limits, and that the preview is never evidence. §13 lists the new tests:
`## Screens` present for a task naming `S2` and absent for one naming none;
the block's content matches the spec rows; an evidence cell citing a preview
fails validation; a preview path given to `/gatekit:design` is refused; the
offer is suppressed after a stop signal and on an input-driven run; exit 0 on
internal error for the new check.

## Rejected alternatives

- **Record per-screen approval in the evidence cells.** This ADR's own first
  draft. It added an approval pass, a confirmed-row convention and a
  validation rule, to produce provenance nobody had asked for. Dropped for
  weight; the corrections themselves are what matter and they live in the
  spec.
- **A gate that checks the built screens against the approved spec.** Drawn
  from the reference harness's structural gates (component reuse ≥ 70%, token
  binding ≥ 90%). Out of scope: the request is to see the design and have
  corrections applied, not to add enforcement, and mechanically checking
  layout fidelity in static HTML is brittle enough to produce mostly false
  failures.
- **More checkpoints through the build.** The reference harness stops four
  times. Each stop costs the owner attention, and the trial's complaint was
  that the process already takes too long.
- **Let the preview file be the evidence.** The laundering decision 4
  prevents.
- **Make the preview interactive.** A second implementation of the product,
  built before the product, with no gates on it.
- **Skip the ADR and write the steps into `mockup.md`.** Prose in a command
  file is never an enforcement mechanism (CLAUDE.md); decision 4 is code.

## Open questions

- Whether `## Screens` should carry the screen's component table as well as
  its layout and states. Left out for prompt size; revisit if workers miss
  components that are named in the spec.
- Whether a preview should be redrawn automatically when `tokens.json` changes
  after the fact. The contract already goes stale (ADR-0008); whether the
  drawing should follow is separate.
